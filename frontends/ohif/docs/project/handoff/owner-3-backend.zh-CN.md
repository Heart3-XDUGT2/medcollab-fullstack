# 给第三人：后端与云端协作交接

日期：2026-10-31  
你的职责：**提供影像服务与可信的协作业务后端，让保存、权限和版本真的成立。**

先读 [三人总览](./README.zh-CN.md) 与 [共同契约 v0.1](./integration-contract-v0.1.zh-CN.md)。接口是供你确认的提议稿，不是已经部署的系统，也不预先要求全部自研。

## 1. 当前前端实际情况

- 已选 OHIF；本机中文体验入口是 `http://127.0.0.1:3000/?lng=zh`。
- 当前尚无团队云端病例/账号/锁/审核服务；不要假设前端已有可用的后端 schema。
- OHIF 能接 DICOMweb，也有原生 SEG/SR/RTSTRUCT 生成/存储链，但它不是完整协作后端。
- 本地导入和 Blob 下载不等于云端上传或项目自动保存。
- 用户本人是第一人，负责工作台；第二人负责 OHIF 适配和医学数据正确性。
- ROI 受控维护和汉化见总览链接，不要求你修改影像算法。

## 2. 请先给团队一张可用的信息卡

请回填共同契约的联调信息卡，并给出以下真实材料：

| 项目 | 必须说明 |
| --- | --- |
| 访问地址 | 队友可访问的开发环境 API 地址；不是你电脑上的 localhost |
| 影像服务 | 实际 QIDO/WADO 地址，STOW 是否支持及限制；HTTPS、认证/CORS 约定 |
| 身份 | 如何以标注员 A、审核员 B 登录；凭证通过受控渠道提供，不写进仓库 |
| 病例 | 实际创建的演示 caseId、归属/分配、源 manifest 和授权 |
| 保存 | 工件如何存入、怎样登记、草稿版本如何提交；至少一个可执行请求示例 |
| 恢复 | 如何按版本获取标注工件并重新打开；不能只返回“上传完成” |
| 并发 | 获取租约、续租、失效和版本冲突的真实响应 |
| 失败 | 401/403/409/412/422 和保存异常的示例 |

地址、认证、真实源数据和一次保存响应都应在开始联合开发时提供，不等全部后端完成后才公开。

## 3. 影像层优先复用现成系统

可评估 Orthanc、dcm4chee 或院内现成 PACS。由你根据部署、许可和集成条件选择，不要求重新开发 DICOM 存储服务器。

你需要：

- 与第二人确认共同公开样例的实际来源及镜像/再分发条款。
- 固定真实 Study/Series/FoR/SOP/frame 清单，不使用业务 caseId 冒充 DICOM UID。
- 明确输入格式、检索与写入能力，处理部分成功、拒绝、网络超时。
- 配置身份验证、授权网关、出口及存储隔离；不能默认公开影像源可以接收私有 token。
- 若使用影像服务器接收 SEG/SR，验证它能检索和返回结果，而不是只接收 HTTP 请求。

部署好影像服务器不是协作业务层验收完成。

## 4. 首轮协作后端范围

优先完成一名标注员、一名审核员围绕一个病例的闭环：

1. 服务端病例可见性、任务归属和操作级权限。
2. 病例级单编辑租约，明确续期和过期；服务端拒绝过期代次和其他用户写入。
3. 实际工件持久化、草稿快照、版本索引和可恢复读取。
4. 提交形成不可变版本，审核通过/退回绑定该版本；旧版本仍可查。
5. 版本锚定的定位评论，身份/时间来自服务器。
6. 关键保存、提交、审核、导出等行为的审计与基础备份恢复。

首轮不要求多人同时画同一块体素、跨机构复杂治理或完整即时消息产品。可以复用身份/存储/消息组件，但框架不是现成病例权限或医学冲突规则。

## 5. 和第二人先确定保存协议

在共同契约给出的两种数据传输实现中，选定第一轮采用哪一种：

- 第二人向受控 DICOMweb STOW 生成结果，你登记验证后形成工件和版本索引；
- 或由你的受控工件接收接口接收结果，再按确认的策略持久化和索引。

不可把选择留给第一人猜测，也不要让第一人重复实现两套。

最低要求：

- 已存储字节与版本索引可对应，源引用和工件归属经过校验。
- 写入校验身份、租约代次和 `If-Match` revision，使用幂等操作 ID。
- 工件已上传但版本索引失败时，不能返回“草稿保存成功”。
- 网络响应丢失后可以查询/幂等重试确定结果，不制造多个不可辨认版本。
- 不存在、未完成或属于其他病例的 artifactId 必须拒绝。

应提供一个实际保存、一个重开、一个版本冲突、一个租约失效的请求/响应示例。

## 6. 给第一人什么，而不是让第一人替你实现什么

你负责返回：

- 有权限的病例列表、业务状态、可执行操作和最新版本。
- 当前编辑占用信息及有效期。
- 明确的保存确认、失败原因和冲突结果。
- 评论和审核记录。

第一人负责把这些结果做成好用的页面。`canEdit` 只是界面提示，真正拒绝无权写入仍由你实现。

## 7. 安全和开发限制

- 只使用共同确认的公开/脱敏样例；不要将真实患者信息放到公网演示、第三方日志或截图中。
- token 不入 URL、日志或仓库；认证方式和 CSRF/CORS 防护一并说明。
- 不提供“跳过认证”的默认生产配置，不把按钮隐藏当授权。
- 机构/病例隔离与版本文件下载必须在服务端检查。
- 备份要有恢复记录，不能只说“已经开启备份”。
- 核对影像服务器、插件及依赖许可；OHIF MIT 不自动覆盖整个部署。

## 8. 你的验收证据

- 一个队友可访问、地址与能力清楚的开发环境。
- 两个身份操作同一病例：A 可写，B 审核/只读，越权请求被拒绝。
- 保存后关闭重开，能恢复实际标注工件与版本。
- 两人争抢编辑、租约过期、版本不一致、网络超时都有确定结果，不能静默覆盖。
- 审核退回后重新提交生成新版本，旧提交及原评论保持不变。
- 提供配置说明、API 样例、测试记录和剩余未实现清单。
