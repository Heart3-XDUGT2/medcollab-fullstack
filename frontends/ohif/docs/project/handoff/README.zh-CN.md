## 4. 先共同跑通这一条流程

共同样例的真实影像、身份与接口信息，见接口约定的“联调信息卡”。

1. 标注员 A 登录，在工作台看到分配给自己的演示病例。
2. A 点击“开始标注”，服务端授权并授予病例级编辑租约。
3. OHIF 打开指定 CT 序列；A 创建一个“演示区域 A”分割。
4. A 保存草稿；服务端确认持久化，界面才显示“已保存”。
5. A 关闭该次编辑，再重新打开；必须恢复同一份标注，而不是仅回到原图。
6. A 提交审核，形成固定版本；审核员 B 打开该版本并定位评论、退回。
7. A 基于退回版本修改，保存并重新提交；B 通过。
8. 历史版本仍可只读重开，评论仍指向原来被评论的版本。

这是首个联调目标，不要求首轮同时编辑同一批体素。建议采用“多人查看/评论、一个病例一个编辑者”的起步方案，三人确认后冻结。

**演示成功不能只看截图。** 要看到远端保存记录、关闭重开恢复，以及另一身份的权限/审核行为。先用 mock 也可以做页面，但必须醒目标识模拟状态，不能作为闭环验收。

## 6. 代码与协作规则

- 尽量通过 OHIF extensions、modes 和 customization 集成，保留上游。
- 第一人调用适配层，不直接访问 Cornerstone 私有状态或自行拼接影像字节。
- 第二人维护影像端和依赖补丁；第三人维护后端 API 和部署。公共组件/翻译资源发生交叉修改时先通知对方。
- 不直接修改 `node_modules`。已验修复必须以正式补丁、版本和锁文件保留。
- 三人的基线必须包含本轮中文修改及正式生效后的 ROI 修复。不能直接另下一个同名 ZIP，就声称与当前代码相同。
- 团队基线已在用户授权下建立并推送，保留上游历史和原仓库初始化提交。第二人后续维护上游同步、分支与补丁，不另起一套互不相干的源码。
- 接口变更先更新共同契约并通知另两人，不各自维护不同版本的字段名。
- 不在 URL、截图、日志、仓库或聊天中传密码、访问 token 或真实患者信息。
