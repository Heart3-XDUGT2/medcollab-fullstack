目标：收敛周一演示的协作流程、标注分工方式，以及现有 OHIF 前端要改多少。

## 0. 结论（先看这六条）

1. **周一不要做“同一序列、多人同时画不同器官”。** 当前 Java 后端是“每人一份整序列二值草稿 + 发布覆盖整序列”，没有多标签、编辑租约、审核和合并。硬做只能得到前端假合并或后发布者覆盖先发布者。
2. **推荐分三层：**
   - **P0（周一）：按病例/序列分工 + 单写者（弱保证）。** 真实登录、影像集权限、私有草稿、发布、版本冲突；前端做最小工作台和保存/发布闭环。
   - **P1（下一阶段）：按切片区块分工。** 同一序列，A/B/C 各负责一段层厚；发布时“自己区间替换、别人区间保留”。这是当前单标签模型下唯一低风险的同图分区。
   - **P2：按解剖部位/器官 + 审核评论。** 需要后端多标签数据模型和不可变提交，不是前端加几个按钮。
3. **“按部位”和“按区块”成本不同。** 器官分工需要多标签、重叠规则和每标签草稿；切片区块只需要坐标归属和块替换合并。当前后端的数据模型能承载后者（整序列 RLE 可按区间切分），但没有区块分配和合并功能；前者需要多标签，当前不支持。
4. **前端不是改一个地址。** 工作台、会话、影像打开、RLE 草稿桥、发布/冲突、协作状态都要新增。**P0 约 12–18 人日（1 人），两人并行约 7–11 天**；以周日到周一约 1.5 个工作日、两名前端并行计算，只够安全回退；极瘦身演示至少也要 2 人并行 2–3 天，完整 P0 不现实。
5. **现有 `medcollab-workspace` 适配器是状态机骨架，不是已接后端。** 它按“病例租约 + SEG 工件 + 不可变版本”设计，Java 实际是“影像集 + RLE 草稿 + 发布版”。保存/恢复的数据面要重写；单测当前在仓库 Jest/Babel 配置下无法启动。可复用约 30–40%，不能按“已完成”排期。
6. **演示必须区分“真实/模拟”。** 真实的是登录、影像集权限、私有草稿隔离、发布、409 冲突；未实现的是租约、审核、器官分区，以及直连 Orthanc 时的像素级权限。不要用界面上的“已保存”掩盖未落库。

### 1.4 三个硬约束

1. **数据模型：整序列、单标签、二值。** 草稿 `PUT` 是整套序列的完整快照，未出现的切片视为全零；发布会用本人草稿替换整条序列的共享掩码（旧 SEG 对象仍在 Orthanc，但业务只暴露最新版）。见交接文档 7.1/7.5/7.7。
2. **协作模型：私有草稿 + 发布版本，没有锁。** 两个用户可以同时编辑，各自草稿互不可见；发布时用 `expectedPublishedVersion` 检查，冲突返回 409。没有编辑租约、审核状态机、评论接口。
3. **影像读取：Java REST 不是 DICOMweb。** OHIF 要 Study/Series UID、方向、间距和实例元数据；`SourceImage` 只有 Orthanc `seriesId`、SOP UID、尺寸，没有 Study/Series UID 和完整几何。Java 也没有给 OHIF 用的受控 DICOMweb 入口。

## 2. 分工方式对比

“分工”有两个层面，不要混在一起：

- **标注分工**：多个标注员怎么分同一个病例的体素/切片。
- **开发分工**：三个人分别交付什么。后者见第 5 节。

### 2.1 标注分工的七种方式

| 方式 | 划分单位 | 冲突边界 | 现有 Java 后端 | 前端改动 | 演示效果 | 风险 | 建议阶段 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 按病例/任务 | 一个影像集/病例 | 无（不同病例） | 支持共享，无“任务/分配”字段 | 工作台列表、角色、筛选；低 | 两人各做一例；第三人只读查看（仅界面，后端未强制） | 低；不像“同图协作” | **P0** |
| 按序列 | 同一病例的不同 CT 序列 | 无（不同序列） | 草稿按序列隔离，支持 | 序列选择器、每序列状态；低-中 | 同病例不同序列并行 | 低；需要多序列数据 | **P0 备选** |
| 按切片区块 | 同一序列的层范围，如 1–40/41–80/81–120 | 区块边界 | 不直接支持；需块归属 + 合并 | 区间限制、他人块叠加、合并、冲突；中 | 同一结构跨层，两人各画一段，合成一个 SEG | 中；边界和擦除要处理 | **P1** |
| 按解剖部位/器官 | 肝、肾、脾、肿瘤等标签 | 标签/重叠体素 | 不支持（单标签、单草稿） | 多标签归属、图例、每标签保存；高 | 临床语义最自然 | 高；后端要改数据模型 | **P2** |
| 按 2D 网格/瓦片 | 一张切片内的矩形块 | 瓦片接缝 | 不支持 | 瓦片网格、跨瓦片编辑、接缝预览；高 | 仅适合病理/WSI 大图 | 高；CT 结构跨块，不推荐 | 不做 |
| 按角色/审核 | 标注员/审核员/仲裁 | 版本状态 | 不支持审核/评论 | 角色只读、版本、评论面板；中-高 | 贴近临床流程 | 中；后端要加状态机 | **P2** |
| 按时间/租约 | 一个病例一个写者，时间片轮转 | 租约到期/接管 | 不支持租约，只有发布冲突 | 占用提示、倒计时、接管；中 | 避免两人同时改 | 中；租约是 BFF/后端能力 | P0 可选 |

### 2.2 先把“按部位”拆成两种

- **大体区**（头/颈/胸/腹/四肢）：如果各区在空间上不重叠，本质上是 3D 区块分工，可归入 P1。P1 先做最简单的切片区间；按 3D 包围盒/多边形划分更灵活，但边界校验和合并更复杂，放到 P1.5。
- **器官/结构**（肝/肾/脾/肿瘤等）：需要多标签、颜色、重叠规则和每标签版本，才是 P2。下面说的“器官”指这一种。

### 2.3 为什么推荐“切片区块”，而不是“器官”
- **单标签限制。** Java 一个序列只有一个二值区域和一个 `label` 字符串。器官分工要求“肝/肾/脾”是不同标签、不同颜色、可独立保存；当前模型表达不了。切片区块只要求“这段层归谁”，仍是同一个二值标签。
- **合并规则可判定。** 切片区块是坐标不重叠的归属：自己的区间用自己的掩码，区间外用最新发布版。器官在空间上可能相邻/重叠，合并需要标签优先级、重叠裁决和每标签版本，规则复杂得多。
- **现有 API 可复用。** RLE 按 `instanceId` 存整张切片的 runs；切片区块天然对应 `masks` 的子集。器官需要新的草稿键（dataset+series+label+user）和多段 SEG，等于重做保存链。
- **演示更真实。** 选一个跨层结构（如肺或体表轮廓），A 画上段、B 画下段，发布后合成一个完整 SEG。观众能看到“同一张图、两个人、各自负责一段、结果合在一起”，而不是两个互不相干的病例。
- **不推荐的绕法：** 为每个器官复制一个影像集/序列，各自发布一份 SEG。表面能并行，但同一序列会出现多份权限、多个版本、多个“病例”，最后无法合成一个标准 SEG；演示可以，产品不要这样做。

### 2.4 为什么 2D 网格不适合 CT

CT 的结构是三维连续的，一个器官/病灶会跨很多切片和瓦片。按 2D 瓦片切会产生大量接缝、重复标注和边界不一致；同一瓦片内还可能同时有多个结构。2D 瓦片只在病理全切片（WSI）这类“图像本身就是瓦片”的场景才自然。CT 的分块应沿切片方向（z 轴），不是屏幕网格。

## 3. 推荐方案

### 3.1 P0（周一）：病例/序列分工 + 单写者（弱保证）

**范围**

- 两个测试账号 A/B，一个**私有**演示病例（或两个私有病例）；公共影像集不能用来演示“未共享看不到”。
- A 在病例 1 标注；B 在病例 2 标注，或被共享后只读查看病例 1 的已发布版（界面只读；当前后端 shared 仍可写，不能声称服务端只读）。
- 目标：同一病例同一时间一个主编辑者。租约可以由 BFF 提供；没有 BFF 时，用“界面占用提示 + 发布冲突”做弱保证，不声称服务端强制单写。
- 真实闭环：登录 → 工作台 → 打开 CT → 画一个区域 → 保存私有草稿 → 关闭重开恢复 → 发布 → 另一账号看到发布版。
- 冲突演示：A/B 都基于 v0 编辑；A 先发布；B 发布时得到 409，保留本地内容，重新载入/合并后再发布。
- P0 的“角色”先用 Java 的 `access`（owner/shared/public）近似；真正的标注员/审核员角色需要 BFF，属于 P2。

**周一的真实/模拟边界**

| 环节 | 周一状态 | 说明 |
| --- | --- | --- |
| 登录、session、CSRF | 真实 | 走 Java/Keycloak |
| 影像集权限、共享 | 真实 | Java 现有 `public/owner/shared`；注意 shared 目前可写，没有只读 |
| 私有草稿隔离 | 真实 | B 看不到 A 的草稿 |
| 发布与版本冲突 | 真实 | `expectedPublishedVersion` + 409 |
| 编辑租约 | 模拟/可选 | Java 没有；BFF 或界面提示，不当作安全边界 |
| 审核/评论 | 不做 | 没有不可变提交和评论接口 |
| 同图分区 | 不做 | 放 P1 |
| 像素级权限 | 取决于数据源 | 直连 Orthanc 时未受 Java 权限保护，必须在演示中说明 |

**最小前端闭环**

1. 工作台：病例列表（全部/公共/我的/共享）、角色/状态、进入按钮。
2. 会话：`/api/session` 引导登录，处理 401、CSRF、退出。
3. 打开：`datasetId + seriesId` → `StudyInstanceUID/SeriesInstanceUID` + 数据源 → OHIF `medcollab` mode。
4. 草稿：标签体素 → RLE → `PUT draft`；重开时 `GET workspace` → 恢复标签图；串行自动保存，只有服务器确认才显示“已保存”。
5. 发布：先确保草稿保存成功，再 `POST publish`；轮询 `GET status`；409/423 保留内容并提示。
6. 协作状态条：`未保存/保存中/已保存/冲突/只读/发布中/已发布`；离开前确认。

**周一不要做**

- 不做器官多标签、审核评论、2D 网格。
- 不在同一条序列上让两个人同时发布而不处理 409。
- 不把“界面禁用画笔”说成服务端权限。
- 不用 mock 的“保存成功”替代真实请求。

### 3.2 P1：切片区块并行

**分工示例**

- 120 层 CT，3 人各 40 层：A `1–40`，B `41–80`，C `81–120`。
- 同一个跨层结构（如肺或体表轮廓）由三人各画自己区间的一段，发布后合成一个二值 SEG。
- 边界规则：相邻区块各多看 2 层作为上下文，但**只有归属者能写**；跨边界的结构以“中心层/多数层”归属，边界层由下一段 owner 复核。演示时明确这条规则。

**合并算法（块替换，不是并集）**

设：

- `P` = 最新发布版掩码（整序列）
- `L` = 本人本地掩码（只含自己区间，区间外必须为零）
- `[a,b]` = 本人负责的切片区间

发布前合成：

```text
M[slice] = L[slice]   if a <= slice <= b
M[slice] = P[slice]   otherwise
```

然后 `PUT draft(M)`，再 `POST publish(expectedPublishedVersion = P.version)`。

- **不能用并集**：如果本人擦除了自己区间内的一笔，并集会把它从旧发布版里“复活”。
- **409 重试**：发布前若 `P` 已变，重新拉取最新 `P`，重新做块替换，最多重试 2–3 次；仍失败则保留本地内容并提示。
- **越界校验**：保存前裁掉/拒绝自己区间外的非零像素；服务端最好再校验一次，不能只靠前端。
- **同一区块只能有一个 owner**：换人时先释放/移交，再基于最新 `P` 重开。

**需要的后端增量**

1. `GET S/published`：返回最新发布版的 `masks`（RLE），不返回本人草稿。这样前端合并只需 RLE 数组，不必解码 SEG。
2. 区块分配：`GET/PUT .../blocks`，记录 `[a,b] → user`；可以放在 BFF，也可以放 Java。
3. **确认发布与草稿 `baseVersion` 的关系**：如果 Java 要求草稿 `baseVersion` 等于 `expectedPublishedVersion`，客户端块替换后仍带旧 `baseVersion` 会被拒；需要后端允许 rebase，或改为“放弃旧草稿 → 以最新 `P` 重建草稿 → 发布”。这一步必须先 spike，不能假设。
4. 发布时校验：掩码不得越界；`expectedPublishedVersion` 必须匹配；同一区块 owner 唯一。
5. 审计：记录谁在哪个区间发布了哪个版本。

**前端增量**

- 区块指示：视口显示“我的区间”、边界层、他人区块的只读叠加。
- 编辑限制：保存前裁剪越界像素；最好在画笔/擦除后立即裁剪，避免用户误以为画上了。
- 合并状态：`仅我的区块` / `已合并他人最新版` / `冲突待处理`。
- 版本/冲突：409 后展示新旧版本，提供“重新合并并发布”，不静默覆盖。
- 代价：**约 +4–6 人日**（不含后端），且需要一次 RLE 合并 spike。

### 3.3 P2：器官多标签 + 审核

**器官分工需要**

- 数据模型：一条序列多个标签/段，每段有名称、颜色、归属、独立草稿或统一草稿里的多段掩码。
- 发布：多段 SEG（或多份 SEG），合并规则、重叠裁决、标签优先级。
- 前端：OHIF 原生支持多标签显示/编辑，但保存链要按标签拆分/合并；工作台要显示每个标签的 owner/状态。
- 这是后端数据模型升级，不是前端开关。**至少 2–4 周**（前后端合计），不要放进周一。

**审核/评论需要**

- 不可变提交版本（当前只有“最新发布版”计数器，历史 SEG 在 Orthanc 里但没有按版本读取的 API）。
- 评论锚点（版本 + 世界坐标/ROI）、角色权限、通过/退回状态机、审计。
- 前端：版本列表、只读审核模式、评论面板、定位跳转。
- **约 +5–8 前端人日 + 后端 5–8 人日**，P2。

## 4. 前端改造评估

### 4.1 可复用与必须重写

按功能面粗估：**阅片/分割约 80% 复用；适配器/驱动约 40% 需要重写；工作台、协作状态和分区是新增。**

**可直接复用（约 80% 的阅片体验）**

- OHIF 影像显示、MPR、工具、Labelmap 分割、撤销/重做、面板、中文资源。
- SEG 读取/导出（单标签、单序列已验证的范围）。

### 4.3 三条集成路径

| 路径 | 做法 | 前端 | 后端 | 风险 | 建议 |
| --- | --- | --- | --- | --- | --- |
| **A. Java 对齐（推荐）** | 前端直接/经薄 BFF 调 Java：workspace、RLE draft、publish、status；新增 `GET published`；租约/审核由 BFF 补 | 12–18 人日 | 3–5 人日 | RLE 桥是新技术点；需一次 spike | 产品主线；一个真相源 |
| **B. 契约 v0.1 BFF** | 保留现有适配器，BFF 提供 cases/lease/artifact/commit；SEG 存 Orthanc，版本索引在 BFF | 6–9 人日 | 6–9 人日 | 与 Java 草稿/发布形成两套版本；权限/编码重复 | 仅在后端愿意维护第二套版本时 |
| **C. Mock 演示** | 工作台 + OHIF 用假数据；保存/发布走内存 | 2–3 人日 | 0 | 不是闭环，不能当验收 | 只用于 UI 彩排，必须醒目标注 |

**推荐 A。** 理由：Java 已经有草稿/发布/SEG 编码和影像集权限，另起 BFF 版本体系会制造“两个真相”。A 的代价是前端要理解 RLE 和 labelmap，但这部分本来就是医学标注前端的核心适配，不应该藏在一个假后端后面。

### 4.4 关键技术风险

1. **RLE ↔ labelmap**：OHIF 的 labelmap 是体积/切片像素，Java 按 `instanceId` 存整张切片的 runs。需要正确处理切片排序、方向、翻转、重采样和 SOP↔instanceId 映射。**先做一天 spike：画一笔 → RLE → PUT → GET → 恢复 → 像素比对**。过不了这个 spike，不要排后续 UI。
2. **影像读取入口**：OHIF 要 DICOMweb 或自定义 DataSource。推荐同源 `/dicom-web` 反向代理，由 BFF/Java 校验 session 和影像集权限；否则直连 Orthanc 会绕过 Java 权限。演示可以临时用公开 CloudFront 的 CT 像素 + Java 掩码，但必须标注“像素读取未受 Java 权限保护”。
3. **草稿恢复**：Java `GET workspace` 有草稿时返回草稿，不会同时返回最新发布版；P1 合并需要新增 `GET published`。不要用“再登录一个账号”绕过。
4. **单标签限制**：任何“多器官/多结构同时保存”的需求都会撞上 Java 的单标签和单段 SEG，必须 P2 处理。
5. **测试与构建**：适配器单测当前 0 执行；新扩展没有构建验证。先修测试，再谈“已验证”。
6. **部署**：Java 无 CORS、无 SPA fallback、静态白名单未覆盖 OHIF 产物；开发期用 3000 + `/api` 代理，正式演示建议同源反向代理。登录回调固定 8080，跨端口会跳回 Java 首页。

## 6. 验收与演示脚本

### 6.1 P0 验收

- [ ] A 登录后只看到自己有权限的影像集；未被共享的私有病例，另一账号看不到。
- [ ] A 画一笔，保存后显示“服务器已保存”；关闭再打开，体素位置一致。
- [ ] B 被共享同一病例后登录，看不到 A 的私有草稿；A 发布后 B 能看到发布版。
- [ ] 弱单写者：A、B 都基于 v0 编辑；A 先发布；B 发布得到 409；B 的本地内容仍在，重新载入/合并后可发布。有 BFF 租约时改为验证“B 只读/接管”。
- [ ] 401/403/404 有明确提示；不静默清空画布。
- [ ] 页面关闭/切换病例有未保存确认；取消不会丢内容。
- [ ] 发布中/保存中按钮禁用；超时后先查状态，不重复发布。
- [ ] 演示中明确标注：租约/审核/像素权限哪些是真实、哪些是模拟。

### 6.2 P1 验收

- [ ] A 只改自己的 `1–40` 层；B 只改 `41–80`；越界像素被裁剪/拒绝。
- [ ] A 发布后，B 发布时保留 A 的区块；B 擦除自己区块内的一笔后，A 的区块不受影响。
- [ ] 边界层结构连续；按约定 owner 复核。
- [ ] A 基于旧版发布时得到 409；重新合并后成功，其他区块不丢。
- [ ] 同一区块不能有两个 owner；换人后基于最新版重开。
- [ ] 合并结果 SEG 的源引用、几何、体素与三人本地掩码一致。

### 6.3 演示脚本（P0，建议 6 分钟）

1. **工作台（1 分钟）**：A 看到“私有病例 1（我负责）”“私有病例 2（B 负责）”；B 看到自己的任务；C 未被共享私有病例 1，打开得到无权限/404。说明这是真实影像集权限，不是界面隐藏，也不是“审核只读”。
2. **A 标注（2 分钟）**：打开私有病例 1，画一个演示区域，保存；状态从“未保存→保存中→已保存”。关闭再打开，标注还在。
3. **私有草稿（1 分钟）**：B 被共享私有病例 1 后打开，看不到 A 的草稿；说明“草稿按账号隔离，发布才共享”。
4. **发布与冲突（2 分钟）**：A 发布 v1；B 基于 v0 编辑后发布，得到 409；B 重新载入/合并后发布 v2；A 刷新看到 v2。强调“没有静默覆盖”。注意：B 有本地修改/草稿时不能被轮询自动应用 A 的新版本，否则冲突演示会变成静默重载。若已有 BFF 租约，则改为“B 只读/接管后发布”，并说明租约是 BFF 能力。
5. **分工说明（30 秒）**：今天演示按病例/序列分工；同一张图的切片区块是下一阶段，已设计好块替换合并，不会用并集造假。

如果被问“为什么不是两个人同时画同一张图的左右/上下”：回答“当前后端单标签、整序列替换；同图并行需要块归属和合并，已列为 P1；周一先把真实保存、权限和冲突跑通，不用假合并冒风险。”
