# 标注统计接口

2026-11-03，版本 v1。配套类型见 `contracts.ts`，调用函数见 `request-examples.ts`。

## 调用约定

统一入口 `http://127.0.0.1:8080`。GET 请求带现有登录 Cookie：`credentials: 'same-origin'`、`cache: 'no-store'`。无需 CSRF，也不需要提交用户名、subject 或笔画数。响应为普通 JSON 对象，不套 `items`。后端返回 `Cache-Control: no-store`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/me/annotation-stats` | 当前登录用户的历史工作量 |
| GET | `/api/datasets/{datasetId}/annotation-stats` | 一个影像集所有 CT 序列的进度与合计 |
| GET | `/api/datasets/{datasetId}/segmentations/{seriesId}/stats` | 一个 CT 序列的进度 |

`datasetId` 为 Java 业务影像集 ID，`seriesId` 为 `/segmentation/sources` 返回的 **Orthanc 序列 ID**，不是 DICOM SeriesInstanceUID。路径参数使用 `encodeURIComponent`。

未登录返回 401。影像集不存在、已删除、没有访问权限或已被移出团队返回 404；未知 CT 序列也返回 404。版本短时间连续变化而无法读取稳定旧版缓存时返回 423，可稍后由用户操作或低频刷新重读。Orthanc/解码失败可能返回 5xx，此时显示读取失败，不要显示成 0。新增接口都是只读，不生成协作房间，不写入新的 SEG，也不申请编辑锁。

## 个人历史统计

```json
{
  "statisticVersion": 1,
  "countingMethod": "accepted-mask-edit-operation",
  "scope": "server-accepted-collaboration-history",
  "historyIncluded": true,
  "totalStrokes": 120,
  "totalAcceptedOperations": 128,
  "paintOperations": 100,
  "eraseOperations": 25,
  "mixedOperations": 5,
  "editedSliceCount": 30,
  "everPaintedSliceCount": 28,
  "editedDatasetCount": 3,
  "editedSeriesCount": 4,
  "firstEditAt": "2026-11-02T08:00:00Z",
  "lastEditAt": "2026-11-03T11:00:00Z",
  "generatedAt": "2026-11-03T11:30:00Z"
}
```

`totalStrokes` 是**被服务器接受、包含非空像素修改补丁的协作操作条数**，字段沿用“笔画”的业务称呼。建议界面显示“累计有效修改 120 次”，旁注“按服务器接受的掩码修改操作统计，含绘制和擦除”。一次鼠标落笔可能被客户端合并、拆分为若干操作，撤销/重做也可能生成补丁，因此不能声称这是精确鼠标落笔数。

计数采用如下规则：

- 一个操作含一个或多个非空切片补丁，计 1 次；同一个批次包含多条操作，逐条计数。
- 标签值大于 0 计入 `paintOperations`；含标签值 0 的擦除补丁计入 `eraseOperations`。二者都有时，也计入 `mixedOperations`，但 `totalStrokes` 只加 1。因此 `totalStrokes = paintOperations + eraseOperations - mixedOperations`。
- 同一已确认 `clientOpId` 的原样请求重试，不重复计数；校验失败、权限拒绝、冲突或整批事务回滚不计数。
- 空补丁、单纯改标签名称或颜色不计入 `totalStrokes`，但计入 `totalAcceptedOperations`。统计依据接受的非空补丁，不逐体素判断提交值是否恰好等于原值；正常前端应继续只提交实际 diff。
- `editedSliceCount` 是历史上本人提交过非空补丁的去重切片数，包含仅擦除的切片。`everPaintedSliceCount` 是其中曾提交过非零标签的切片数，后续擦除不会减少。它表示本人曾绘制过几张切片，不能据此认定本人是掩码首位创建者。
- 切片去重键为 `datasetId + seriesId + instanceId`；相同 CT 导入到不同业务影像集分别算。`editedDatasetCount`、`editedSeriesCount` 仅统计含掩码修改的历史范围，纯元数据修改不算。
- 按 `issuer + subject` 识别用户，用户名改名不清零。团队移除成员或影像集逻辑删除后保留本人历史总数，但不因此恢复其影像访问权限。接口仅返回本人合计，不泄露已无权限的影像集明细。
- 首次升级时从全部现有 `mask_ops` 分批补算；重复启动和重复补算不增加结果。`historyIncluded: true` 表示现存协作操作历史已纳入，**不表示没有日志的早期手工上传能还原笔画**。
- 浏览器 IndexedDB 中尚未同步的私有草稿、在本地导出的 SEG、早期仅上传 SEG 而没有协作操作日志的行为不包含在本统计中。最早/最近修改时间在从未修改时为 `null`。

历史累计与“目前剩多少掩码”是不同数据。擦除会增加历史工作量，同时可能降低 CT 完成度。

## CT 序列进度

```json
{
  "datasetId": "dataset-id",
  "seriesId": "orthanc-series-id",
  "progress": {
    "totalSlices": 100,
    "annotatedSlices": 40,
    "unannotatedSlices": 60,
    "ratio": 0.4,
    "percent": 40.0
  },
  "publishedProgress": {
    "totalSlices": 100,
    "annotatedSlices": 38,
    "unannotatedSlices": 62,
    "ratio": 0.38,
    "percent": 38.0
  },
  "seq": 130,
  "throughSeq": 125,
  "publishedVersion": 4,
  "pendingArchive": true,
  "archiveError": ""
}
```

| 字段 | 含义 |
| --- | --- |
| `progress` | Java 当前已接受的共享画布进度；没有协作房间时取当前已发布 SEG |
| `publishedProgress` | 当前已经写入 Orthanc 并登记成功的最新 SEG 进度 |
| `totalSlices` | 当前业务影像集中、该序列受支持的单帧 CT 原始切片数量；不包含 SEG/SR 等派生文件 |
| `annotatedSlices` | 至少有一个非零掩码像素的 CT 切片数量；一张上画多个标签仍只算一张 |
| `unannotatedSlices` | `totalSlices - annotatedSlices` |
| `ratio` | `[0,1]` 的未舍入比值 |
| `percent` | `[0,100]` 百分数，四舍五入到小数点后两位；前端不要再乘 100 |
| `seq` / `throughSeq` | 当前已接受操作序号 / 当前已归档操作水位 |
| `publishedVersion` | 最新已发布 SEG 版本号；尚未发布为 0 |
| `pendingArchive` | `seq > throughSeq`，仍有操作等待或正在归档；可能只有标签名修改，两个进度值相同也可为 true |
| `archiveError` | 现有归档错误提示；空字符串表示当前无错误提示，不代表没有排队 |

在一张 CT 上只画一个像素，也会将该切片算作“已有标注”；完全擦空后不再算。**完成度只表示非空掩码切片覆盖率，不表示器官已经完整标注，也不表示医学质量通过审核。** 多平面绘制的统计最终按实际源 CT 切片计算，不按屏幕视窗数计算。

私有 IndexedDB 未同步的内容不会出现在这两个值中。前端若要显示“本机尚未同步的进度”，应另列状态，不能把本机值冒充服务器统计。没有发布过 SEG 时 `publishedProgress.annotatedSlices=0`；已发布版本被全部擦空时，即使计数为 0，版本号仍可大于 0。

## 影像集合计

返回 `DatasetAnnotationStats`：`datasetId`、`completionMethod`、`seriesCount`、`progress`、`publishedProgress`、`pendingArchive`、`series`、`generatedAt`。`series` 每项与上面的序列响应一致。

合计对切片数求和，再计算比例。例如序列 A 为 1/2、序列 B 为 0/1，总计是 1/3 = 33.33%，不是平均两个百分比得到 25%。没有可标注 CT 的影像集返回空 `series` 和 0 张、0%，不会被当成 100%。只计算当前业务影像集的切片，不会为补齐同一 DICOM UID 越权读取其他影像集。

每个序列的当前画布与归档元信息使用一致的数据库读取快照；多序列合计是在逐序列读取后生成，持续协作时并非跨所有序列冻结的全局瞬间。普通读取使用已有掩码 JSON/统计缓存，不下载 CT 像素；升级前最新 SEG 缺少切片计数时，仅首次读取需要下载和解析该 SEG，并缓存结果，不扫描全部历史 SEG。

## 前端接入和兼容要求

1. 个人中心调用 `personalAnnotationStats()`；影像详情/列表展开时调用 `datasetAnnotationStats(datasetId)`；工作台只需当前序列时调用 `seriesAnnotationStats(datasetId, seriesId)`。不要每一笔都刷新整个影像列表。
2. 已有操作确认后或收到协作变动后，合并刷新当前序列统计；归档完成后再读一次。建议防抖或低频刷新（例如 5–10 秒），不要并发堆积轮询请求。WebSocket 仍使用既有协议，本次没有新增统计推送事件。
3. 切换账户、切换影像集或卸载页面时取消旧请求，或用上下文版本号丢弃迟到响应；个人统计响应不带用户名，不能用旧结果覆盖新账号。
4. 继续使用现有 IndexedDB、操作提交、编辑权、自动归档、覆盖清理和成品下载链路。本次新增统计 GET，不要求修改任何已有写接口、JSON 请求体或草稿 schema，不要为了更新数字自行再发布 SEG。
5. CT 完成度是所有有权编辑者共同的当前结果；个人总修改数是该用户终身历史，两者不要相互推算。错误时保留上次成功值并显示状态，401 走现有重新登录流程，404 隐藏失效影像，423 可以稍后重读。

后端健康检查 `/api/health` 增加 `annotationStatsApi: "v1"`，可据此确认部署版本。前端没有强制增加新的统计 UI，接手开发者可以按上述契约自行排版。
