# SEG 覆盖清理并发修复

2026-11-06。代码与安装包已完成，启用状态以 `installed-manifest.json` 和实际 `/api/health` 为准。

## 改动

普通 DICOM 导入（含文件流入口）、手动发布和协作自动归档共用 `SegmentationStorageGuard`。引用写入使用共享读锁，清理使用独占写锁。锁在上传开始前取得，直到数据库真实提交或回滚后才释放；加入外层事务时通过事务完成回调释放，不会把内层方法返回误当作提交。

清理候选查询仍可在锁外执行，实际删除前必须在独占锁内重新检查全部引用。锁覆盖替代文件检查、物理 DELETE 和清理回执提交。上传正在进行时，清理跳过当前周期，下一轮重试；多路上传可并行。

自动归档保护编码、上传、待完成任务的 Orthanc ID 登记、发布记录及任务完成状态，避免上传已成功但任务引用尚未登记的空档。失败释放锁，已有重试队列、幂等记录和旧版本下载重试逻辑保留。

## 兼容性与范围

- 业务 HTTP 路径、请求体、Labelmap SEG 格式、登录和共享规则不变，无需修改前端或迁移数据库。
- 健康检查新增 `segmentationStorageGuard: "single-process-rw-v1"`，原有 `segmentationStorage: "latest-only-v1"` 等标记保留。
- 保护范围是同一个 Java 进程经业务服务发起的存储操作。外部直接操作 Orthanc 不受这把锁保护；将来若多个 Java 进程连接同一存储，需要数据库或其他跨进程协调。
- 绘制操作、浏览器 IndexedDB 草稿不取得此锁。已有清理正在执行时，导入/发布/归档可能短暂等待；每个文件清理后就释放独占锁，不把整批 32 个文件放在同一独占区间。

## 启用

双击本文件夹内 `启用SEG清理并发修复.cmd`。脚本会核对校验和、停止本项目 Java、备份旧 JAR 与已关闭的 H2 数据库、安装新包、启动并检查健康标记。启动失败时回退旧 JAR。账号、CT、SEG 和前端沿用原有数据与配置。

脚本拒绝覆盖准备修复后又被其他任务更新过的 JAR，以免退回新的后端功能。安装成功后仍用桌面“01-一键启动全部”。只打开首页不能证明修复已启用，必须核对实际健康标记。

## 维护位置

- `backend/src/main/java/com/example/demo/SegmentationStorageGuard.java`
- `DatasetService.java`：两种导入入口。
- `SegmentationService.java`：手动发布事务和自动归档辅助方法。
- `CollaborationService.java`：自动归档完整保护范围。
- `SegmentationRetentionService.java`：独占清理及锁内引用复核。
- `HealthController.java`：部署核验标记。
- 回归测试：`SegmentationRetentionConcurrencyTests`、`SegmentationStorageGuardTests`、`SegmentationRetentionTests`。

所有存储新入口都必须先取得引用保护，再取得团队/数据集数据库锁，并保持到实际事务完成。不要只在 Orthanc POST 周围加锁、在登记引用前释放；不要只在删除前增加一次无锁查询。
