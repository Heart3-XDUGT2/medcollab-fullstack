# NIfTI 导入与个人数据集删除：后端对接建议

日期：2026-11-06。

状态：需求与接口建议，**不是已实现或已联调的能力声明**。本次仅核查源码、编写文档，没有上传文件、删除数据、变更数据库、后端或 OHIF。已有上游修复（包括 `3666836`）不在本任务修改范围。

接收方：Java / 存储后端、OHIF 工作台维护者、Portal 前端。

## 1. 推荐优先级与交付边界

| 优先级 | 建议交付 | 不能据此宣称 |
| --- | --- | --- |
| P0 | Portal 提前识别 `.nii` / `.nii.gz` 并说明当前不支持；继续保留 DICOM 导入 | NIfTI 已支持，或改扩展名即可导入 |
| P1 | 个人数据集安全逻辑删除；复用团队删除的授权、数据可见性与引用保护规则 | 已物理清除原片、已追回他人下载或本地草稿 |
| P2 | NIfTI 单个三维影像最小闭环：导入、授权读取、正确显示、标注持久化、关闭重开、结果导出 | 任意维度/模态、标签文件导入、训练导出均已支持 |
| P3 | 经独立验收后再扩展既有标签导入、多个 volume、四维时序、批量/断点上传 | 这些扩展可混入 P2 验收 |

建议先交付 P0/P1，NIfTI 由后端与工作台共同估算后单独实施。不要仅增加上传后缀、让 Orthanc 接收文件，或增加无法保存的浏览器 loader，就宣布支持。

## 3. NIfTI：先约定对象与几何，再约定上传

### 3.1 必须区分的两类输入

- **影像 volume**：连续或离散标量强度数据，作为标注的源影像。`.nii` / `.nii.gz` 只是容器与压缩形式，不代表一定是 CT。
- **labelmap**：整数标签体素，必须绑定一个已存在、已授权且几何吻合的源影像及标签定义。不能按文件名、尺寸相同或“看起来像掩码”自动配对。

P2 推荐只接收明确声明为影像的单个三维标量 volume；标签输入、向量/RGB、四维/更高维、复数等在支持前明确拒绝。不要由强度值猜测“影像还是标签”。NIfTI-1/NIfTI-2、支持的 datatype 和维度清单由后端/工作台共同确认并写进能力说明。

### 3.2 数据与坐标契约

以下均为**必须新增或明确的契约要求**，不是现有字段：

- 数据集下引入稳定的源影像对象标识；一个 NIfTI volume 不等于一个 DICOM 实例，不把业务 datasetId 当成 Study/Series UID。
- 记录源格式、原件校验和、字节大小、维度、datatype、体素 spacing、空间单位、原始 qform/sform 与选用的 voxel-to-world affine。原文件名仅作受控显示，不能充当路径或授权。
- 明确索引轴顺序、体素中心约定、左右手系、RAS/LPS 的转换、切片方向与原点。qform/sform 冲突、缺失/奇异 affine、非有限数值、单位不明应拒绝或要求显式确认，不能静默翻转/猜测。
- 若重排轴、重采样或生成派生 DICOM，保存不可变的源→派生变换、处理版本及原始几何；不能改源头坐标来“适配显示”。
- 掩码绑定稳定源对象及几何版本，不仅绑定序列名称；导入标签必须校验整数标签、shape、affine、标签值范围与映射。几何不一致默认拒绝，不静默最近邻重采样。
- 原件受授权保留，可校验下载；派生物与原件具有同一访问边界。原件和标签可能含敏感信息，不进入源码、公共静态目录、日志或外部转换服务。

**明确推荐**：以“原件 + 受控派生对象 + 可追溯几何”为业务事实，单独评估与现有 CT/SEG 链兼容的工作台方案。若选择转换 DICOM，必须验证强度缩放、方向、UID/序列身份、源关联及 SEG 引用，不伪造 CT 模态、患者信息或临床来源；转换成功不是全链路验收成功。

### 3.3 P2 的最小闭环验收

1. 经授权导入一份非患者测试 volume，服务端识别内容与几何，不只看扩展名。
2. Portal 展示真实导入状态；完成后工作台打开指定源对象，不误开独立 CT 样例。
3. 用已知左右/前后/上下标记和非等距 spacing 的测试体验证三平面、方向、测量与强度；不得仅凭截图“像一张图”。
4. 绘制标签，服务端保存可校验版本；关闭页面、清除工作台内存并重开后，源影像、几何、标签和版本一致。
5. 导出结果保留正确 source/geometry/label mapping；至少一种约定结果格式能被独立工具重读并比较体素。建议先提供源几何一致的 NIfTI labelmap 及元数据清单；是否还需 DICOM SEG 由工作台团队确认。
6. 换账号、失权、数据集删除、并发保存冲突均不能串读/串写；在未通过以上项目之前不开放正式“NIfTI 支持”标识。

不要把 NIfTI 全部计入现有“CT 帧覆盖率”；当前统计分母是受支持 CT。若需新 volume 统计，另定语义与版本，未知状态不得显示 0%。

## 4. NIfTI 异步导入建议（Proposed）

现有 `/api/import` 维持单个 DICOM 与原响应，不直接改变为异步或混用返回类型。建议新增独立协议，避免破坏旧 Portal、团队库和批量 DICOM 导入。

| Proposed 方法与路径 | 建议含义 |
| --- | --- |
| `POST /api/datasets/{datasetId}/imports` | multipart 单原件 + 明确的 `kind=image`；确认身份、权限、CSRF 后创建异步任务 |
| `GET /api/datasets/{datasetId}/imports/{importId}` | 仅有权限的账号读取任务状态；不因知道 importId 获得原件 |
| `POST /api/datasets/{datasetId}/imports/{importId}/cancel` | 尽力取消，不承诺撤回已完成的提交；成功完成后不当作删除数据集 |

以上路径、字段、状态码**都未实现，需队友定稿**。新适配器建议显式支持 POST 的 `202`，不要让现有只接收约定成功响应的 DICOM 适配器误判。

Proposed 状态最小集合：`queued`、`validating`、`processing`、`succeeded`、`failed`、`cancelled`。返回稳定 importId、状态、受控错误 code/message；成功后返回源对象 ID，不返回裸磁盘路径或长期带权 URL。不提供无依据的百分比或 ETA。任务创建/接收中断与处理失败要区分。

推荐要求：

- 客户端操作 ID / 幂等键作用域为账号 + dataset + 操作；同键同内容返回同任务，同键不同内容冲突。键名、保存期限和恢复查询方式需定稿；超时未知不得自动重复创建。
- 上传前与任务正式提交前重新授权；团队仍校验当前成员资格。处理期间被移除、数据集被删或账号上下文变化时，任务不能晚到挂接到已不可访问的资源。
- 默认按一个任务提交一个完整 volume：验证/处理失败不得在业务列表留下半个可打开的影像；原件可留隔离区待清理，必须有状态可核对。
- 压缩字节限额、解压后体素字节限额、维度乘积、CPU/内存/磁盘配额、并发与处理超时都需服务端限制；`.nii.gz` 不能只检查 1 GiB 压缩包大小，防解压膨胀、坏头和截断内容。
- 不假定当前 DICOM 1 GiB / 30 分钟即适合 NIfTI。具体值由后端以部署配置发布，网关、multipart、任务 worker 与前端提示一致。
- 暂存区使用随机内部 ID，拒绝路径穿越，不按原文件名写路径；失败、取消、重启后恢复或清理有明确 TTL 与可重试回执；清理不能删除仍被任务/业务引用的文件。
- 异步任务遵循服务器账号/资源授权，不靠长时间持有旧浏览器 Cookie 工作；任务状态查询过期会话返回 401，隐藏/不存在资源按统一策略返回 404。
- 建议错误区分：不支持格式/维度、几何不明确、损坏数据、超限、失权、取消、存储暂不可用、处理失败。具体状态码/code 由合同确定，不把所有情况变成“网络异常”。
- 成功、失败、重启与网络丢响应均可通过任务查询核对；新能力未启用时 Portal 明确提示不支持，不降级成把 NIfTI 发到 DICOM `/api/import`。

建议由部署能力显式声明协议是否启用和限额；能力标记名称待定，不擅自假定 `/api/health` 已有新字段。

## 5. 个人数据集逻辑删除建议（Proposed）

### 5.1 资源、权限与产品冲突

建议新增 `DELETE /api/datasets/{id}`，只处理个人、非公共数据集；推荐成功 `200 {"success":true}`，与现有团队删除适配一致。**此接口当前不存在**。

- 服务端按 issuer + subject 校验数据集创建者；用户名、列表 `access`、客户端 `canDelete` 都不是授权依据。共享接收者、普通登录者不能删除，公共集不开放个人删除。
- 团队数据集继续走现有团队路径和“当前成员 + 创建者”规则；不能用个人新接口绕过离队后的权限限制。
- 对创建者的重复删除返回同样成功；删除前后均可校验 tombstone 归属。不让未知/他人数据集通过幂等响应泄露存在性；身份无效为 401，已可见但非 owner 的删除为 403，不可见/不存在按 404。
- **共享冲突必须确认**：当前个人共享一经确认不可撤销。删除共享数据集会使所有接收者失去该资源，并不只是“从我的列表移除”。推荐最终语义是 owner 明确确认后对整个资源逻辑删除，但必须经产品批准并更新共享说明；批准前最小上线策略为已共享数据集返回明确 409，不暗中推翻旧共享规则。
- 不将“取消收藏”“从最近移除”“退出共享”伪装成删除。后两者不能替代资源级删除；当前也没有退出个人共享能力。

### 5.2 事务、协作与引用保护

- 使用现有 `deleted_at` 思路，删除提交后所有账号的列表、统计、workspace、DICOMweb、原件下载、labelmap、发布、协作/租约与任务入口都必须拒绝后续访问；逐入口测试，不只隐藏首页。
- 与导入、重命名、共享、画笔操作、快照/归档任务取得一致资源锁。删除与写入只能有明确先后：写已提交则保留其记录后删除；删除先提交则禁止迟到写重新激活或追加影像。
- 推荐首版遇到尚有效的协作租约/未完成写入任务返回 409，提示结束操作后由用户再次确认；不加无协议的“强制删除”。有效判定以服务端租约/任务为准，不用前端在线人数。到期租约需可靠释放，不能永久阻塞。
- 同一次事务隐藏对应所有收藏/最近引用，或让所有 activity 读取严格过滤已删除资源；推荐保留内部引用以便审计，不在 API 返回名称/统计等残留。分页 total、favorite state、最近打开去重/迟到事件同样不能复活数据。
- 首版不物理删影像、SEG、标签版本、原件或共享引用，继续保留 tombstone 和必要审计。浏览器 IndexedDB 草稿、已下载文件不能远程追回；提示用户本地草稿未自动销毁，重新提交仍须服务端授权。
- 不因数据集逻辑删除而擅自扩大现有 latest-only SEG 清理范围；当前版本、其他数据集引用、快照任务、待完成导入/发布引用必须继续保护。
- 物理回收单独立项：保留期、恢复策略、审计要求、全局引用复核与后台幂等回执齐备后才能做。回收站/恢复 API 当前不存在，前端不能承诺可撤销。

必须保留 `SegmentationStorageGuard` 与上游 SEG 并发修复。涉及物理对象新引用/清理时沿用现有保护直到真实事务提交/回滚，不能只锁 Orthanc POST 或在登记引用前释放。具体锁顺序与团队→数据集锁兼容，由后端统一评审；不能为删除功能改出反向锁顺序。

## 6. 前端接入条件与即时格式提示

P0 可先独立落地：

- 在 `upload.ts#validate()` 的统一入口用不区分大小写的 `\.nii(?:\.gz)?$` 识别并提前拒绝；`.nii`、`.nii.gz` 及混合大小写均覆盖，ZIP 原逻辑保留。
- 提示建议：“暂不支持 NIfTI（.nii/.nii.gz）导入，当前仅支持 DICOM 文件或文件夹。”
- 文件选择附近保留简短实际格式说明。不要仅靠 `accept=".dcm"`，无扩展名 DICOM 仍应可选；后缀识别是反馈优化，不替代服务器内容校验。
- 不改扩展名、不自动转换、不把 NIfTI 发送失败当作已导入。混选中存在不支持格式时，按当前整批预校验阻止创建/导入，并指出文件，不先创建空集再报格式错误。

删除接入须等待真实 API 和协议确认：展示服务端能力/权限、明确影响范围并二次确认；新鲜 session + 动态 CSRF；账号变化/卸载/离开上下文取消等待。超时、断网、5xx 只表示结果不确定，读取列表核对，不自动重试 DELETE 或声称回滚成功。成功后清除本页选中/详情并重新读取真实活动与列表；不要只从一个组件数组删行。

## 7. 联调验收清单

| 场景 | 必须得到的结果 |
| --- | --- |
| `.nii` / `.NII` / `.nii.gz` / `.NII.GZ`，混合 DICOM + NIfTI | P0 即时说明不支持，整批不发业务写；合法无扩展名 DICOM 不受误伤 |
| ZIP、空文件、超限、伪装后缀 | ZIP/空/超限按真实规则拒绝；服务端仍按内容验证，后缀改名不绕过 |
| 三维各向异性体、斜位/负轴 affine、qform/sform 冲突 | 支持项几何正确；不支持或不明确项显式失败，无静默翻转 |
| gzip 膨胀、截断文件、异常维度、worker 重启、丢响应 | 有资源上限与可查状态，清理可恢复，无重复对象/半成品可见 |
| 标签 shape 一样但 affine 不同、未知标签值、4D 影像 | 未支持时拒绝，不自动绑定、静默重采样或仅取第一帧 |
| NIfTI 标注保存后关页重开、导出独立重读 | 源身份、方向、强度、标签体素与版本一致，权限有效 |
| owner 删除未共享个人集，再重复删除 | 两次成功，所有业务读取拒绝，逻辑记录/物理原片按约定保留 |
| 接收者删除、匿名、伪造 owner、他人 issuer | 后端拒绝，不因前端显示或 URL 参数放行 |
| owner 删除已共享集 | 按已批准产品规则执行；未批准前明确 409，不出现“仅本人隐藏”的假删除 |
| 删除期间他人正协作、上传、发布或生成快照 | 锁序一致；明确冲突或串行顺序，无死锁、迟到复活或误报已取消 |
| 同一 CT/SEG 被别的个人/团队数据集引用 | 删除一个集不影响另一个集像素、当前标注和 SEG；无物理误删 |
| 删除后收藏/最近分页、统计、旧 workspace/下载链接、旧草稿提交 | 无残留泄露或写入；本地已下载内容不假装已追回 |
| 团队创建者离队、组长删别人、重复删自己 | 继续符合现有团队规则；个人接口不能成为绕过路径 |
| 新接口未部署、回退旧版本 | 原 DICOM、团队删除、共享、CT 统计和 SEG 清理保持兼容；前端不展示不可用操作 |

真实联调必须使用获授权的非患者测试数据和独立账号，标明实际服务版本/能力与请求结果。mock、代码存在、底层库支持或构建通过均不等同以上闭环通过。

## 8. 请队友确认后再编码的事项

1. 个人共享不可撤销与 owner 全资源删除如何协调；建议批准全局删除前，先对已共享集明确 409。
2. 个人删除是否采用本稿路径/200 响应与幂等策略；首版是否接受活跃协作/任务冲突 409，暂不开放物理清理和恢复。
3. NIfTI 首版精确支持的版本、datatype、三维影像范围、几何判定与工作台实现责任；是否同意标签导入/4D 后置。
4. NIfTI 新协议、任务存储/重启恢复、原件保留、压缩/解压/资源限额、任务/暂存 TTL、幂等和能力声明由谁负责并提供样例。
5. 标注存储与结果导出格式及源几何映射，后端和 OHIF 共同给出能重开/能独立重读的验收证据。
