# 统一资料库、团队收藏与团队解散：前端对接说明

日期：2026-11-07。此文描述本轮后端新增协议，以及前端需要接入的页面功能。后端启用状态以实际 `GET /api/health` 为准；交付 JAR 不等于正在运行的服务已更新。

## 一、前端这轮需要做什么

| 页面或操作 | 前端要做的内容 | 调用接口 |
| --- | --- | --- |
| 我的资料库 | 在现有界面接入“全部／个人／团队／公共”来源筛选，团队选择、全局搜索、服务端分页 | 新增 `GET /api/me/datasets` |
| 团队资料 | 展示真实团队名称；支持收藏、取消收藏，收藏后可从首页收藏入口打开原团队资料 | 复用现有收藏列表、状态及 PUT/DELETE 接口 |
| 团队管理 | 只向组长展示“解散团队”，确认会清空全队资料和标注，再提交操作 | 新增 `DELETE /api/teams/{id}` |
| 解散后的清理状态 | 需要展示清理进度时查询，pending 为 0 即停止 | 新增 `GET /api/teams/{id}/dissolution-status` |
| 文件选择和上传 | TXT/PDF/普通图片/文档/压缩包等提前报不支持；混选时整批预检通过后再创建数据集 | 原 `POST /api/import`，增加明确的格式拒绝 |

本轮只改后端和交接文件，Portal/OHIF 页面尚未增加以上按钮、分区或上传预检。

## 二、先检查后端能力

`GET /api/health` 新增：

```json
{
  "datasetLibraryApi": "v1",
  "teamDissolutionApi": "clear-library-v1",
  "dicomImportFormatPolicy": "known-nondicom-reject-v1"
}
```

原 `homeActivityApi: "v1"`、`teamApi: "team-library-v1"`、`sharingPolicy: "personal-forward-copy-v1"`、`datasetDeletionApi: "unreferenced-reclaim-v1"`、`workspaceApi: "dicomweb-labelmap-v1"` 等保留。

- 有 `datasetLibraryApi: "v1"` 再使用统一资料接口；旧后端继续个人/公共原列表及“选定团队→团队库”入口，不在浏览器遍历所有团队拼装全量结果。
- 有 `teamDissolutionApi: "clear-library-v1"` 再显示可用的解散操作。能力已声明而接口返回 404 时要区分接口不匹配与具体团队已失权，不显示为成功或空列表。
- 业务数据和接口均同源，通过 Java；不暴露 Orthanc 管理地址或持久带权 URL。

## 三、统一资料列表

```http
GET /api/me/datasets?source=all&page=0&size=20&sort=created-desc&q=胸部
```

| 参数 | 规则 |
| --- | --- |
| `source` | `all` 默认；`personal` 仅本人持有的非公共个人集，含转发收取的独立副本；`team` 本人当前团队资料；`public` 公共资料 |
| `teamId` | 可选，仅与 `source=team/all` 共用；只返回指定团队资料。当前非成员或团队已解散返回 404 |
| `q` | 可选，去首尾空白，最多 100 个 Java 字符；数据集名称、业务 ID、创建者显示名中不区分大小写的字面子串；中文可匹配，`%`、`_` 是普通字符。不会搜索像素或 DICOM 标签 |
| `page` | 从 0 开始，不小于 0；超过末页返回空 items，保留真实 total |
| `size` | 默认 20，范围 1–100 |
| `sort` | 首版仅 `created-desc`，按 `created_at DESC, id ASC`；不支持的值 400 |

示例响应（示例编号均为占位值）：

```json
{
  "items": [
    {
      "id": "dataset-business-id",
      "name": "团队胸部 CT",
      "access": "shared",
      "ownerUsername": "上传者",
      "instanceCount": 139,
      "createdAt": "2026-11-07T00:00:00Z",
      "scope": "team",
      "teamId": "TM-0123456789ABCDEF",
      "teamName": "胸部研究组",
      "uploaderSubject": "uploader-subject",
      "canDelete": false
    }
  ],
  "total": 1,
  "page": 0,
  "size": 20,
  "sourceCounts": { "personal": 2, "team": 1, "public": 2 }
}
```

示例中当前 source 筛选可以为 team，所以 total 为 1，而来源计数仍包含筛选前另外两类。

### 字段与计数边界

- `scope` 仍只有 `personal/team`。个人和公共项均为 `scope=personal`；公共通过 `access=public` 区分。不要把 `scope` 改成三个值。
- 个人转发副本是接收者的 `access=owner` 独立 ID。团队项对本上传者为 owner，其他当前队员为 shared；团队 shared 可共同编辑，不表示个人共享授权。
- 个人/公共项 `teamId/teamName/uploaderSubject=null`。团队项返回真实 `teamId/teamName/uploaderSubject`。
- `canDelete` 只描述该条数据集当前可否删除，不代表可以解散团队。公共 false；本人个人集 true；团队仍仅上传者可删除自己的数据集。个人和团队删除要走各自入口。
- `instanceCount` 是关联 DICOM 实例数，不是标注完成度或病例数。CT 进度继续读标注统计接口。
- `total` 已按权限、q、teamId 和 source 过滤，再在分页前计数。
- `sourceCounts` 按权限、q、teamId 过滤，**不受当前 source 选择限制**。指定 teamId 后 personal/public 为 0。
- 同名资料、不同行为产生的独立业务副本分别计数；相同 Orthanc 文件不会把业务数据集合并。收藏、最近不会重复创造资料条目。
- 权限、计数、页面在同一数据库读取快照中计算。固定排序保证一个快照内的次序，页码分页不保证并发新增/删除时跨页绝不漂移。
- 切换来源、团队、搜索条件时重置页码；不要对当前页做本地排序、筛选来冒充全库结果。使用后端 total 和 sourceCounts。

成功 200 JSON/no-store；参数无效 400、未登录 401、指定团队不存在或无权 404。未知错误正常提示，不伪造空列表。

## 四、团队收藏使用已有接口

```text
GET    /api/me/favorite-datasets?page=0&size=20
GET    /api/me/favorite-datasets/state?datasetId=A&datasetId=B
PUT    /api/me/favorite-datasets/{datasetId}
DELETE /api/me/favorite-datasets/{datasetId}
GET    /api/me/recent-datasets?page=0&size=20
```

收藏状态查询一次 1–200 个 ID。可访问项返回真实布尔值；被省略的项是未知/失权，不可直接视作 false 后允许盲写。收藏写成功仍按现有 `{success,datasetId,favorited,favoritedAt}` 响应更新；未知写结果不自动重试。

收藏只增加本人快捷引用，**不复制 CT、不改变归属、不赋予访问权限**。团队成员仍操作同一团队业务 ID。离队/被移除/解散后不能靠收藏和旧链接继续访问；收藏/最近列表会过滤失权资料，解散还会移除该团队资料的活动引用。

最近打开仍由工作台真实成功打开回执登记，不因列表出现、点击收藏或失败打开而记录。活动摘要目前不提供 canDelete/uploaderSubject，不从活动项的 owner 推断删除按钮，管理操作回到团队或统一列表的真实上下文。

## 五、组长解散团队并清空团队影像

```http
DELETE /api/teams/{teamId}
```

无请求体，需要当前登录会话和动态 CSRF。

建议前端确认文字：

> 解散团队将移除全部成员，并清空团队内所有人的影像和已保存标注，包括尚未归档的协作修改。该操作不可撤销。其他个人或团队独立持有的资料不受影响。

200 示例：

```json
{
  "success": true,
  "teamId": "TM-0123456789ABCDEF",
  "deletedDatasets": 3,
  "deletedObjects": 0,
  "retainedObjects": 0,
  "pendingObjects": 278
}
```

- 仅当前组长可解散。队员 403；非成员、未知团队等 404；未登录 401；CSRF 缺失/失效 403。
- `deletedDatasets` 是本次解散时仍活跃并被删除的数据集数，重复 DELETE 返回原计数。此前已经删除的团队集也会补做存储清理，但不增加这个计数。
- 成功后团队不再出现在我的团队或团队搜索，邀请码失效，原成员无法再读取、上传、编辑、加入或创建该队资料。全部上传者的团队数据都会清空，组长无需成为每个数据集的上传者。
- 保留内部删除回执和团队关联，防止旧团队资料被误认为上传者的个人资料；不会自动把团队影像分给成员。
- 团队原片、所有 SEG、服务端草稿、协作掩码/编辑权/待归档任务及收藏/最近引用会删除或进入受保护的回收流程。历史个人贡献统计保留；用户已下载文件和浏览器 IndexedDB 草稿不受远程删除影响。
- 后端会等待进行中的受保护上传/归档完成后再清空，因此请求可能需要等待。提交后立即按“团队已解散、文件清理中”展示，不要求 pendingObjects 当场归零。
- 存储按唯一 Orthanc 对象计数：仍被其他活跃个人/公共/团队数据集、当前 SEG 或未完成归档引用的对象保留；只回收无人持有的对象，逐实例处理，不删除整个 Study/Series。
- 后台清理失败会持久保留 pending 并重试；不因此恢复团队。没有回收的对象不等于团队仍可访问。

### 查询解散结果与清理状态

```http
GET /api/teams/{teamId}/dissolution-status
```

返回同一结构。仅实际完成解散的原组长可查；尚未解散、其他账号或未知团队返回 404。建议低频轮询，例如每 3–5 秒，pendingObjects=0 或离开页面后停止。

DELETE 对该原组长幂等，已完成后的重复提交不会重新创建团队或重复登记清理。请求超时或取消时不能宣称后端已回滚：查询状态核对；404 只能表示当前没有可查的成功回执，不能独自证明进行中的请求一定失败。保留相同 teamId，重新确认会话并让用户核对，不能自动重试操作。

成功后清除对应列表、详情、选择状态、团队资料及活动缓存；其他成员在下次请求/协作权限复核时也会失权。遇 401/403/资源 404 取消旧请求并清敏感上下文，丢弃迟到响应。

## 六、上传格式与空数据集

原 `POST /api/import` multipart：字段仍为 `file` 和 `datasetId`，成功响应不变，且继续使用流式上传和现有大小上限。

- `.nii/.nii.gz` 仍明确 415，不支持 NIfTI。
- 常见非 DICOM 后缀提前 415：txt/md/csv/json/xml/yaml/yml/pdf/png/jpg/jpeg/gif/webp/bmp/tif/tiff/svg/doc/docx/xls/xlsx/ppt/pptx/rtf/htm/html/zip/7z/rar/tar/gz/nrrd/nhdr/mha/mhd/npy/npz/stl/obj/ply/vtp/vti/mp4/avi/exe/dll，大小写不敏感。
- 无后缀、未知后缀、`.dcm/.dicom/.ima` 仍可提交给 Orthanc 做内容校验。MIME 不作为唯一依据，不要求必须存在 DICM 前导。
- 文本改名 `.dcm` 不能绕过 Orthanc 的内容校验；无效内容沿用 400。后缀拒绝只提供更早、更明确的错误，不是证明文件有效。
- 415 响应仍是 JSON `{ "error": "…" }` 和 no-store；空文件 400、超限 413。
- 后端不会自动删除已经独立创建成功的空数据集，创建和逐文件导入也不是一个原子批次。前端必须在创建请求之前统一预检整批文件，避免 TXT 失败留下空集；已经成功导入的其他文件不自动回滚。

## 七、按钮路由与兼容规则

| 资料 | 打开/标注 | 删除 |
| --- | --- | --- |
| 个人 owner（含转发副本） | 现有工作台启动流程，使用该业务 ID | `DELETE /api/datasets/{id}`，需 canDelete=true |
| 公共 | 现有启动流程 | 不提供删除 |
| 团队 | 现有启动流程，使用团队资料 ID | `DELETE /api/teams/{teamId}/datasets/{datasetId}`，需 canDelete=true；仍只删除本人上传项 |
| 整个团队 | 团队详情 | 组长使用新增 `DELETE /api/teams/{teamId}`，会清全队资料 |

继续复用已有 createHomeApi、Cookie 会话、fresh session issuer+subject 核对和动态 csrfHeaderName/csrfToken；不要新增密码 JSON 登录，也不要把 token 放到 URL。切账号、卸载、切团队或失权时取消旧 scope，丢弃旧响应和待发写入。

旧 `/api/datasets`、单队列表、个人转发、个人/团队单项删除、工作台 DICOMweb、SEG 和统计协议保留。此轮未增加个人资料“复制到团队/移动到团队”接口，不用个人转发或“复制后 DELETE”拼接实现移动。

## 八、前端验收清单

1. 统一入口按真实权限展示三类来源；搜索/分页/计数一致，改筛选后页码归零，同名和独立副本不混淆。
2. 团队条目可收藏并出现在首页收藏中，打开仍为原团队 ID；离队和解散后立即清理前端缓存，后续访问失败。
3. 团队单项删除仍只对上传者开放；解散按钮仅组长可见，确认会清所有成员资料，成功后退出团队上下文。
4. 解散状态可查询；pending、retained、deleted 区分清楚；超时不误报回滚或自动重试；原组长重复提交不会重复清理。
5. TXT、PDF、图片、ZIP、NIfTI 及混选在 create 前拒绝；合法无扩展名 DICOM 仍可上传；伪装 `.dcm` 的文本显示服务端拒绝。
6. 缺能力时诚实降级；未知收藏状态不盲写；旧服务、登录、工作台、独立转发和个人删除保持兼容。
