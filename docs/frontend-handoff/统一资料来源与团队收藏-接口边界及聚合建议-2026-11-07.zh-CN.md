# 统一资料来源与团队收藏：接口边界及聚合建议

日期：2026-11-07。核查基线：`main` / `96e65b8`。

本文区分现有能力与 **Proposed（待实现建议）**。仅只读源码与测试、编写此文；未请求真实用户资料，未上传、转发、收藏或删除数据，未修改后端、OHIF、Portal 实现、产物、服务或 Git。后续实现以最新源码和实际部署能力为准。

## 1. 结论与本轮最小交付

用户已接受统一资料入口：按个人、团队、公共来源找资料；收藏和最近打开跨来源。收藏仅为本人引用，不复制资料、不改变权限；团队仍共同编辑同一团队数据集。

**现在即可交付**：首页明确提供团队来源入口，选择本人所属的某个团队后，进入其独立团队库，或只懒加载该选中团队的列表。在团队数据集行接入现有收藏 API。名称、来源、收藏状态与失败提示使用真实服务响应。

**当前不能宣称**：已实现所有团队资料的统一分页、全局搜索、准确全量来源计数。不要在浏览器遍历所有团队并请求每队列表后拼装“全量资料”；这会产生请求放大、部分失败漏数、跨请求权限变化和无法正确分页的问题。

**补充需求**：还需支持把平台内已有的个人数据集加入团队，而不是要求用户下载后重新上传。建议优先交付“复制到团队”，再单独交付“移动到团队”；接口、快照和验收要求见第 7 节。该能力与收藏、统一列表聚合不同，当前尚未实现。

## 2. 当前接口事实

| 接口 | 现状与边界 |
| --- | --- |
| `GET /api/teams` | 本人当前所属团队；可复用 `api.listTeams()` 作为团队选择器，不表示团队资料总表 |
| `GET /api/teams/{id}/datasets` | 当前团队成员可读的该队全部未删除数据集；没有服务端 `page` / `size` / `q` 参数 |
| 团队列表响应 | `{items,total}`，`total=items.size()`；排序 `created_at DESC, id ASC`。不是跨团队总数或分页前总数 |
| 团队页面搜索 | `TeamsPage` 对已读取的当前团队数据集做本地筛选，不能当成全局服务端搜索 |
| `GET /api/datasets` | 排除团队集，返回本人个人集及公共集。个人收到的转发副本是自己的新业务 ID，不再靠旧个人 `shared` 授权读取发送者原 ID |
| 收藏列表 | `GET /api/me/favorite-datasets?page=0&size=20`，已支持个人、公共和当前可访问团队集；服务端分页且权限过滤先于 total / 分页 |
| 最近列表 | `GET /api/me/recent-datasets?page=0&size=20`，同样跨来源；真实成功打开由工作台上报，不因选中、浏览元数据或失败启动就增加历史 |
| 收藏状态 | `GET /api/me/favorite-datasets/state?datasetId=A&datasetId=B`，1–200 个 ID；可访问项返回真实布尔值，失权/不存在项省略 |
| 收藏写入 | `PUT` / `DELETE /api/me/favorite-datasets/{datasetId}` 已支持团队。收藏前仍校验资料访问权；移除本人收藏引用在失权后也可执行，不赋予影像权限 |
| 能力门禁 | 已有 `homeActivityApi: "v1"`；部署未声明时，不请求缺失的活动接口，不制造空收藏或成功写入 |

### 模型复用

当前团队列表 `TeamDatasetItem` 提供：

```text
id, name, access(owner/shared), ownerUsername, instanceCount, createdAt,
scope(team), teamId, uploaderSubject, canDelete
```

此响应**没有 `teamName`**。进入选定团队后，可用已验证的 `Team.name` 显示上下文，不把前端补充展示值说成接口原字段。

收藏 / 最近项的嵌套 dataset 摘要已提供 `scope`、`teamId`、`teamName`；当前摘要**没有 `canDelete` / `uploaderSubject`**。不能从 activity 的 `access=owner` 直接推断个人删除权限。团队详情和管理仍走真实团队上下文。

`scope=personal` 包括个人和公共资料；公共由 `access=public` 区分。“个人/团队/公共”是入口来源分类，不要把现有 `scope` 类型直接改成三个值。业务 datasetId、teamId 都不是 DICOM Study/Series UID。

### 复用与安全要求

- Portal 已有 `createHomeApi`、`listTeamDatasets`、`favoriteStates`、`setFavorite`、`useHomeActivity`，不需要后端重新开发“团队收藏”。前端应先复用，不另起一套假收藏存储。
- 团队切换、账号变化、退出示例、卸载或失权时先取消旧 scope，再清旧数据；丢弃迟到结果。已知 datasetId 在批量状态中被省略时为未知/失权，不当成“未收藏”后允许盲写。
- 保留同源 Cookie、新鲜 session 的 issuer + subject 比较及动态 CSRF；服务端逐次授权仍是权威。未知写结果不自动重试。
- 401/403 遵循已有会话安全阻断；团队资源 404 清当前失权上下文，不能继续显示缓存私有资料。集合接口不匹配与单资源失权不得混用文案。
- 团队资料收藏、最近打开、入口跳转不调用个人转发接口，不创建副本。个人转发仍按 `personal-forward-copy-v1` 生成独立业务副本；团队共同编辑和团队删除规则不变。

## 3. 需要后端补的统一聚合接口（Proposed）

推荐新增只读 `GET /api/me/datasets`，避免改变现有 `/api/datasets` 与团队列表的非分页契约。**当前没有该接口，以下路径、字段和能力名称均需队友确认。**

### 请求建议

| 参数 | 建议规则 |
| --- | --- |
| `source` | `all`（默认）/ `personal` / `team` / `public`；personal 排除公共及团队，包含本人持有的转发副本 |
| `teamId` | 可选，仅 `source=team/all` 时允许；服务端验证当前成员资格，不能仅靠知道 ID 读取 |
| `q` | 可选，去首尾空白、上限 100 字符；匹配数据集名称、业务 ID、创建者显示名的字面子串。大小写/中文匹配规则明确；不把 `%` / `_` 当 SQL 通配符 |
| `page` / `size` | 从 0 开始；size 建议默认 20、最大 100，校验越界与偏移溢出 |
| `sort` | 首版推荐只支持 `created-desc`：`createdAt DESC, id ASC`。新增名称排序时明确数据库排序规则和 ID 次序，不由前端对单页排序冒充全局排序 |

### 响应建议

```text
{
  items: DatasetSummary[],
  total: number,   // 当前账号权限过滤 + q + source + teamId 后、分页前数量
  page: number,
  size: number,
  sourceCounts: { personal: number, team: number, public: number }
}
```

- 建议条目复用 `id/name/access/ownerUsername/instanceCount/createdAt`，并完整返回 `scope/teamId/teamName/canDelete`；若统一入口需要现有团队删除控件，还应返回团队 `uploaderSubject`，而非让前端猜测。
- 个人和公共项 `scope=personal`，`teamId/teamName=null`；团队项 `scope=team` 且带真实团队元数据。公共项 `canDelete=false`；团队能力按当前成员及创建者计算。按钮提示不是授权凭证。
- `sourceCounts` 必须先应用当前权限、`q` 及有效 `teamId`，再按三类来源分别计数，**不应用当前 source 选择**；`total` 则再应用 source。这样明确为什么筛选后 total 不等于三类计数之和。若首版不提供计数，就不显示猜测的全量数字。
- 个人转发副本按不同业务 ID 计不同条目，不能因复用同一 Orthanc 文件而合并；同一团队业务 ID 也不能因收藏、最近或多个引用重复计数。
- 权限过滤、计数、分页应在同一一致性读取中完成。离队、被移除、删除后不得泄露旧名称、团队名或条目/总数。不可访问的指定团队按既有策略 404。
- 固定排序保证同一数据快照内的次序；页码分页不承诺并发新增/删除时跨页绝不漂移。高频变化场景后续可加 cursor/snapshot 协议，不在本轮伪造强一致承诺。
- JSON/no-store/同源 Cookie 沿用当前契约，建议成功 200；无效参数 400、未登录 401、无权资源 404、暂不可用 503。具体规则由合同定稿，不返回裸 Orthanc 路径或永久带权 URL。

### 能力与兼容

建议通过健康能力声明增加 `datasetLibraryApi: "v1"`（**Proposed，当前不存在**），且仅在新协议完整可用时启用。旧 `/api/datasets`、团队列表、活动分页与收藏写入保持兼容。

旧服务降级为个人/公共原列表与“选定团队 → 独立库”入口。声明有能力却返回 404 时提示接口版本不匹配，不把它当作空资料或全部失权，也不在后台退回全团队遍历。

## 4. 无效格式与空数据集

现状依据：`upload.ts#runUpload` 先调用 `createDataset`，成功后才逐文件 `importFile`；后端 `/api/import` 将单文件交给 `DatasetService#importDicomFile` 与 Orthanc 校验。

当前前端预检拒空文件、超限、NIfTI 和 ZIP，但没有明确排除 TXT。TXT 导入失败只影响该文件的关联事务，**不会回滚先前独立创建请求**，所以可能留下真实的空数据集。不是“前端列表显示了一条假成功导入”就能解释的现象，也不能宣称整个批次原子回滚。

前端可立即改进：将 TXT/PDF/常见图片、办公文档等明确非支持格式集中在统一预检函数中拒绝；在选择文件时即说明，并在整批验证通过前不创建/导入。仍允许无扩展名和可能的 DICOM 扩展名，不能仅 `accept=".dcm"` 或改后缀。MIME 可能缺失/错误，不能作为唯一真伪依据。

后端 Orthanc 内容校验仍权威：改名 `.dcm` 的文本仍应失败。DICOM 不一定含 Part 10 的 `DICM` 前导标志，不能用一次 magic 检查把所有无前导 DICOM 拒掉。前端不承诺证明文件有效，也不新增重量级影像解析依赖。

服务端若需更好的类型错误，建议对已知明显不支持格式补清晰的 415（目前仅 NIfTI 有明确早期拒绝）；不自动删除空集，不擅自删除“所有文件均失败但创建成功”的真实资源。后续若要原子导入/临时数据集提交，应单独约定，不混入本次聚合接口。

## 5. 队友确认与验收

请确认：是否接受新只读聚合路径、分页/排序与计数语义；是否返回完整来源及可操作能力；能力字段和上线版本；搜索字段/长度/排序规则；已知无效格式的后端错误分类。**团队收藏不属于待补接口。**

## 7. 个人数据集加入团队（补充需求，Proposed）

补充日期：2026-11-07。当前团队接口支持创建数据集、上传本地文件和移交组长，**没有把既有个人数据集复制或移动到团队的接口**。`/api/teams/{id}/transfer` 只是移交组长，个人 `/shares` 只是转发给个人账号，均不能拿来替代本需求。

### 7.1 推荐交付顺序与产品语义

| 操作 | 个人来源 | 团队目标 | 推荐顺序 |
| --- | --- | --- | --- |
| 复制到团队 | 保留原 ID、内容和个人管理权限 | 创建新业务 ID，取得一致性快照，此后由团队共同编辑 | 优先交付 |
| 移动到团队 | 成功后不再作为个人资源访问 | 转为团队资源，按团队成员和管理规则访问 | 单独定稿、独立验收后交付 |

前端入口建议是个人数据集菜单的“加入团队”，以及团队库的“从个人资料库导入”。用户选择已有资源和目标团队，不重新上传 CT 文件。首版只提供复制时，动作必须明确叫“复制到团队”，不得显示成移动或暗示原件会消失。

收藏只是快捷引用；复制生成独立业务数据集；移动改变资源归属。三者不得共用含糊的“同步”提示。复制完成后双方标注不再自动同步；若要继续共同编辑，应打开团队目标而不是个人原件。

### 7.2 复制到团队的最小接口建议

以下路径、字段与成功响应都是 **Proposed**，不是现有契约：

```text
POST /api/teams/{teamId}/datasets/copies
{
  sourceDatasetId: string,
  operationId: string
}

200 {
  success: true,
  operationId: string,
  sourceDatasetId: string,
  dataset: TeamDatasetItem
}
```

- 调用者必须拥有来源个人数据集，并在提交时仍有目标团队的创建资料权限。按 `issuer + subject` 核对，不能仅凭“可以查看来源”允许复制；首版排除公共和团队来源。
- 目标返回真实的新业务 ID、`scope=team`、`teamId` 及团队列表已有的创建者/操作能力字段。目标名称默认继承来源；若允许改名，沿用名称校验。业务 ID 不等于 DICOM UID。
- 创建者登记为实际执行加入操作的成员，后续删除沿用团队规则，不自动给组长新增“删除所有资料”的权限。复制者退出团队后，目标留在团队，个人原件不受影响。
- 同源 Cookie、fresh session 身份比较、动态 CSRF 和取消边界沿用现有写接口。服务端必须再次授权，前端按钮不是授权凭据。
- `operationId` 在账号、来源和目标团队范围内幂等；同操作重试不得生成多个团队副本，同 ID 换参数应冲突。必须提供凭操作 ID 核对结果的方式，具体查询路径由后端定稿。请求超时或取消不能被前端当作已回滚，也不得自动换 ID 重试。
- 不按同名或相同 CT 文件自动判定“已经复制”。是否允许用户明确再次创建新快照由产品确认；同一操作幂等与多次主动复制是两个规则。
- 沿用现有成功 200 JSON 约定。无效输入、失权、目标不存在、来源繁忙及存储失败应给明确分类；具体状态码由后端定稿，建议冲突/暂不可快照为 409，不把失败显示成成功空集。

### 7.3 标注快照、存储与一致性

复制默认包含来源影像，以及服务端已经接受的当前标注状态；目标能在工作台重开，不只是列表出现一个空壳。若首版只支持影像、不支持携带标注，必须明确作为受限版本，不能使用“完整复制”文案。

- CT 等不可变原片可复用现有 Orthanc 对象引用，无需浏览器下载或重复上传；目标独立登记引用，来源或其他副本删除不能清掉目标仍持有的对象。
- 标注快照应明确所用源版本，涵盖当前 SEG 和已接受但尚未归档的掩码；引用、版本和目标归属必须一致。不能只复制旧 SEG 后静默丢失最新编辑，也不能把同一可变画布绑定给双方继续写。
- 复用个人转发的快照和存储保护机制前，需审查团队权限、目标标注版本初始化及锁顺序，不能直接向现有个人收件人字段塞入 teamId。
- 不复制浏览器 IndexedDB 草稿、其他人的私有草稿、在线成员、编辑租约、光标、操作流或原账号的终身贡献统计。不因创建副本生成“成功打开”的最近记录。
- 若首版无法在活动编辑或待归档状态下取得一致性快照，返回 409，提示关闭工作台并等待保存后重试；不能偷丢未归档编辑。后续允许在线快照时另行定义一致性边界。
- 来源删除、离队/被移除、并发编辑和后台物理回收，都必须与复制提交协调。创建目标、登记原片与标注引用应原子完成；失败不留下可见的半成品或未受保护的存储引用。
- 必须保留现有存储引用锁直到事务提交，物理回收在受保护状态下重新检查引用。不得通过删除整个 Study/Series 清理失败副本。
- 只有快照任务确实无法在同步请求内可靠完成时，才升级为异步任务协议；异步状态、结果查询、取消及临时资源清理需一并定义，不能返回成功后让前端猜完成时间。

### 7.4 移动到团队必须另行确认的规则

首版复制不等于移动。**禁止前端用“复制成功后再调用个人 DELETE”拼接移动**：复制与删除之间可能失权、出现新编辑或发生网络中断，无法提供可靠的移动结果。

如后续支持移动，需要服务端专门操作，并明确：

1. 来源 ID 是否保留。建议首版移动保留 ID、原片和标注版本，仅原子变更业务归属；若数据库或工作台不允许，必须明确返回新 ID、旧 ID 的访问结果及引用迁移规则，不能前端猜测重定向。
2. 来源只允许本人拥有的非公共个人集；目标权限在实际提交时重新校验。团队的创建者、删除权、移除成员及离队规则需要用户确认，移动者不能被误导为离队后仍拥有个人访问权。
3. 编辑租约、未归档掩码、后台归档任务存在时，首版应阻止移动并返回可恢复的冲突，不允许在旧权限下继续写。不能把已经接受的编辑清空来完成移动。
4. 本人的收藏和最近引用如何随归属变化；失去访问权的旧引用应过滤，不能依靠引用继续访问。列表来源、权限、活动摘要和统计应一致更新。
5. 其他账号已经持有的独立转发副本不受影响。移动不能追回他人的副本、下载文件或本地草稿。
6. 同一移动操作须幂等，结果可查询，目标关联与个人归属移除原子提交。错误、取消和超时不得留下“双方都没有”或“已移动但仍可按旧权限写入”的状态。

### 7.5 能力声明、验收与队友确认

建议为复制、移动分别声明能力（名称待定，例如 `teamDatasetCopyApi: "v1"` / `teamDatasetMoveApi: "v1"`）。只支持复制就只展示复制，旧服务不出现可点击的假导入入口；不改变现有本地文件上传或个人转发协议。

复制交付至少验收：

- 本人个人资料复制到本人有权限的团队后，返回新 ID、目标可由其他当前团队成员打开，原个人资料仍存在。
- 已发布标注与服务端当前掩码按约定完整携带；目标修改、来源修改互不影响；本地未提交草稿不被冒充为已复制。
- 相同操作重复提交只有一个目标；真正再次复制的行为符合定稿规则；超时后能查明结果而不是盲重试。
- 非本人来源、公共/团队来源、已删除来源、非成员目标，以及提交中失权均不能创建副本或泄露资料。
- 复制与来源删除、编辑/归档、后台回收并发时，不丢原片、不漏保护引用、不留下可打开的半成品。
- 复制后删除来源，目标仍可打开；复制者离队，目标仍留在团队，离队者不能再通过收藏或旧链接访问团队目标。
- 个人/团队列表、来源摘要与准确计数反映真实归属，不因复用物理影像而合并两个业务对象；原团队收藏和删除权限不退化。

请后端与工作台队友确认：先交复制还是两者都做、接口与幂等查询方式、快照所含标注及繁忙条件、锁和事务边界、目标创建者规则、能力名称、移动 ID 与活动引用处理，以及上线版本。此需求优先于进一步视觉美化；与第 3 节的只读聚合接口可分别交付。
